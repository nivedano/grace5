Installed GRACE skills have one owner and a verifiable installation-health state

Brief for approval. Change C-0014-installation-ownership, revision 1, 2026-11-17. Full brief, written by: independent reader.

What you get

  • Installed grace5-* skill directories under .agents/skills/ and .claude/skills/ have one owner: the package. A project mirror generator keeps validating project-owned skills and never rewrites those installed directories, so the same candidate can no longer fail and pass because excluded files changed.
  • A dedicated installation-health tool compares every installed grace5-* directory with the packaged skill bytes and the state pin, prints the differing paths, writes nothing and exits nonzero on drift. A missing packaged skill source is an actionable error, not a pass.
  • Installation health is evaluated afresh at handoff and is not candidate evidence: a required check that depends on excluded inputs is not candidate evidence unless a bounded dependency fingerprint is separately approved, and this change adds no fingerprint mechanism.
  • upgrade.md, source-identity.md, grace5-prepare and grace5-execute state the ownership and handoff-time freshness rules, and the existing refresh stays the only writer of installed packaged skills.
  • Release identity does not move: no version, pin, tag, migration row, new kernel command or new automatic project-file write, and project-owned skills stay outside the installed directories.

Decisions for review

  • D1Installed packaged skill directories are owned by the package; a project mirror generator validates only project-owned skills and never rewrites those directories.
  • D2Installation health is evaluated afresh at handoff and is not candidate evidence; a check result on an earlier candidate never makes an installation pass current.
  • D3No dependency fingerprint is introduced by default; it is admitted only by a separate approved contract for a real required check that cannot be separated from installation health.
  • D4Drift is reported, not repaired automatically; the existing refresh remains the only writer.
  • D5The health tool reads the pin and the installed bytes and writes nothing, so it changes no candidate and needs no owner gate of its own.
  • D6A failing assertion is never deleted to make the installation green; the ownership conflict is resolved instead.

Risks

  • Drift is reported and never repaired: a broken installation stays broken until someone runs the existing refresh, so a failing health run is a state to fix at handoff, not a result about the candidate.
  • No fingerprint mechanism is added, so a retained required check that genuinely cannot be separated from excluded inputs stays without candidate evidence and must be re-established at every handoff.
  • The ownership rule binds a project mirror generator by documentation and review: this repository implements no client generator, so nothing in the kernel enforces the client side.
  • Health is compared against the packaged bytes and the pin of the checkout that runs the tool, so a stale or locally modified kernel checkout reports drift that is local state rather than a product defect.
  • A green health run can be mistaken for evidence: it never substitutes for a candidate check, an owner approval or a receipt.

Approval decisions and effort

  • Rule on the ownership decision: installed packaged skill directories belong to the package, and a project's mirror generator keeps validating only project-owned skills.
  • Rule on the deferred fingerprint: admitting one needs a separate approved contract, and none is added by this change.
  • Accept that installation health is a handoff-time state and not a closing condition, so its pass is retaken rather than carried as evidence.
  • See that the client-side change happens where the mirror generator lives; this framework repository supplies the rule and the tool, not the client implementation.
  • Read the guidance text itself: the automated checks show the packaged copies are in sync, so judging what upgrade, source-identity and the lifecycle guidance actually say is a reading task.

Left alone on purpose

  • N1: no automatic repair or rewrite of installed skills; drift is reported and the existing refresh remains the repair path.
  • N2: no arbitrary dependency fingerprint, cache hash or hash of all GRACE records; a fingerprint needs its own approved contract if a real required check cannot be separated.
  • N3: no weakening of a required check and no deletion of an assertion to turn an installation failure green.
  • N4: no new kernel command, receipt field or migration boundary.
  • N5: no client-specific mirror-generator implementation inside this framework repository.
