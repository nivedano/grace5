Preparation proves evidence is feasible and discriminating before approval

Brief for approval. Change C-0016-feasible-evidence, revision 1, 2026-11-17. Full brief, written by: independent reader.

What you get

  • Preparation identifies, for every required check, the device, build and environment state and the observation, before you commit to the plan.
  • Preparation uses the read-only diagnostics that are available to establish whether each required device and environment is available, and reports what it cannot establish as unknown.
  • When required evidence is unavailable, you get one bounded choice before approval: wait for the evidence, or accept alternative evidence with its stated limitation.
  • The brief's evidence discussion names a plausible faulty implementation the check would reject; for a trace it also names the setup whose absence would fail, so a bare missing marker cannot pass.
  • Feasibility is a preparation obligation, never the final observation, and it authorizes no flashing or hardware-state change.
  • The behavioural evidence for the guidance is a manual rehearsal on a change whose required device, build or environment is unavailable; the automated checks only show that the edited sources compile and that the generated packages carry them.
  • The pilot's focused regression test and position rule remain separate governed work.

Decisions for review

  • D1Feasibility is a preparation obligation, not evidence: an available device or environment is established before the owner commits to the plan.
  • D2An availability that cannot be established is reported as unknown, never as available and never as a product failure.
  • D3When required evidence is unavailable, the owner receives one bounded choice before approval: wait for the evidence, or accept alternative evidence with its stated limitation.
  • D4The brief names a plausible faulty implementation the check would reject; a trace also names the setup whose absence would fail, so a bare missing marker cannot pass.
  • D5The pilot's focused regression test and position rule are separate governed work, not an implicit extension of this framework change.
  • D6The shared-bookkeeping-path scheduling rule stays until a concrete safe exception demonstrates full-diff ownership and evidence invalidation.
  • D7Feasibility work uses read-only diagnostics and never flashes, resets or changes hardware state.
  • D8The rehearsal is the behavioural evidence for the guidance; the automated checks prove only that the edited sources compile and that the generated packages carry them.

Risks

  • Read-only diagnostics may report a device or environment as available while the observation later fails, so feasibility can be established from evidence that does not predict the bench result.
  • The alternative-evidence branch lets approval rest on weaker evidence than the original check, with the limitation stated but not enforced.
  • Nothing in the kernel requires a brief to name a plausible faulty implementation, so the new guidance can be satisfied perfunctorily or skipped.
  • A named faulty implementation may be trivial to reject, giving false confidence that the check discriminates.
  • Preparation effort grows for every change, including those whose devices are plainly available.
  • The guidance's only behavioural evidence is a manual rehearsal, so it is easy to perform superficially or skip, and its result depends on the one prepared case and the person running it.

Approval decisions and effort

  • Rule, when required evidence is unavailable, between waiting for it and accepting alternative evidence with its limitation, before approval.
  • Confirm that a required manual or trace check's device, build and environment state can be established; a bench session is needed where it cannot.
  • Approve this framework change on its own: the pilot's focused regression test and position rule need their own contract and approval.
  • Confirm the amended or added rationale-ledger entry carries the smallest alternative and a removal criterion.
  • Keep the guidance change free of any check kind, schema, receipt, command or approval-semantics change.
  • Run the rehearsal session on a change whose required device, build or environment is unavailable, and judge whether the guidance behaved as required.
