The kernel refreshes installed skills only from committed skill text and pins LF for every text file

Brief for approval. Change C-0011-clean-skill-source, revision 1, 2026-11-16. Full brief, written by: independent reader.

What you get

  • A refresh cannot install uncommitted skill text: when the chain contains a migration step and the running kernel checkout's skills/ or packages/skills/ differs from its HEAD, grace5 upgrade refuses before it prints the plan and before it writes anything, names each modified path, and exits 1. The same refusal holds with and without --plan.
  • The guard is deliberately narrow: a chain of pin bumps is not refused, a kernel checkout without .git is not checked, and no flag overrides the refusal. A clean kernel source upgrades exactly as it does today.
  • Installed copies stay out of scope: a governed repository's grace5-* skills are neither inspected nor repaired, so drift there remains undetected rather than becoming a new obligation.
  • The repository pins line endings through a new .gitattributes holding * text=auto eol=lf. The index is already LF on all 231 tracked files, so the rule renormalises no blob, rewrites no file and alters no record.
  • The refusal is stated where a person meets it: the command help, upgrade.md, commands.md and a new conformance case. No installed skill byte, state layout, command, flag, schema or record changes, and the version, pin, tag and migration table stay as they are.

Decisions for review

  • D1The guard covers both kernel trees: the canonical skills/ that authors edit and the packages/skills/ that a refresh reads. Either being dirty refuses, and the refusal names the paths. Both are covered because guarding one leaves the other as the way uncommitted text reaches a governed repository.
  • D2The guard runs only when the chain contains a migration step. Only a step refreshes skills; a pin bump reads no skill file, so it is neither refused nor slowed, and the check stays out of the path that changes nothing but the pin.
  • D3The refusal precedes the plan and every write, --plan included: a plan that describes a refresh the kernel would not perform misleads more than a refusal does, so the order is refusal, then plan, then writes.
  • D4Two residuals are accepted rather than closed: a kernel checkout without .git is not checked, and a clean but untagged checkout is accepted. A tag or commit-ancestry requirement is out of scope, so the guard tests the working tree, not the provenance of HEAD.
  • D5Installed-skill drift is neither detected nor repaired. The change protects the kernel's own source, not the installed copies in a governed repository, whose staleness therefore stays as it is today.
  • D6The repository rule is * text=auto eol=lf. The index is already LF on all 231 tracked files, so the rule renormalises no blob and alters no record; it is configuration, not a kernel mechanism, and carries no ledger entry.

Risks

  • The guard is only as wide as git's report. A file under skills/ or packages/skills/ that is gitignored or marked assume-unchanged does not appear in the status the guard reads, so it would be installed by a refresh with no refusal. The contract states three residuals and not this one.
  • A legitimate edit in the kernel's own skill trees now blocks every upgrade whose chain contains a step, until it is committed. There is no override flag, so the only ways forward are to commit or stash the work before upgrading.
  • A kernel distributed without .git is unchecked by design: its skill source is whatever the installed package holds, so an operator who edits the installed package gets no refusal, and nothing records that the check was skipped.
  • The line-ending rule is repository-wide, not skill-only. Every text file is pinned to LF, so a file that must keep CRLF later needs an exception rule, and the pin is evidenced by two sampled files rather than by the trees or the index.
  • Installed-skill drift remains undetected, so a governed repository can run stale grace5-* skills while every check of this change passes.
  • The documented refusal rests on review. No check reads upgrade.md or commands.md, so a document that drifts from the implemented condition fails no check.

Left alone on purpose

  • N1: no deletion or consolidation of the skill copies. packages/ and skills/ stay as they are; the one-copy or single-channel design waits for the installation process.
  • N2: no drift detection or repair for installed skills, in status or in upgrade; drift stays outside the target contract.
  • N3: no installer, no seeding, no skill-location change and no new skill; installation remains separate from the kernel.
  • N4: no tag or commit-ancestry enforcement. A clean but untagged checkout is still accepted; only a dirty skill source is refused.
  • N5: no change to run, check, close, status, or to the refresh semantics of a step.
