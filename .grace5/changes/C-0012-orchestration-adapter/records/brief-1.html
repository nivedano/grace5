One lifecycle adapter over harness task facilities, with bounded role handoffs

Brief for approval. Change C-0012-orchestration-adapter, revision 1, 2026-11-17. Full brief, written by: independent reader.

What you get

  • grace5-orchestrate becomes one thin lifecycle adapter: the harness's native task facilities own spawning, messaging, waiting, cancelling, inspection and transient progress, while GRACE keeps authority, isolation decisions, phase selection and closure.
  • One implementer is active at a time in a shared worktree. Implementers run baseline, targeted and final evidence, and the orchestrating agent validates status and the complete diff at handoff instead of repeating fresh evidence on an unchanged candidate.
  • Preparation is a lifecycle phase of the triggering conversation, not a separate session: a requested material revision is contracted and independently briefed there, only the unresolved owner decision is asked, execution waits for approval of that revision, and an approval of the exact unchanged bytes is reused without a new question or record.
  • Live progress stays in native task state. One compact prose checkpoint under .grace5/orchestration/runs/ records the workspace, selected and excluded changes, original starts, worker identity and deadline where not otherwise recoverable, fix-round count, parked obligations and unsettled decisions, holding only what is not durably recoverable.
  • Dispatch packets are role-bounded and carry verified repository and documentation roots, shell convention, change id, original start and current candidate, permitted role and return stage. Reviewer packets carry the approved contract, complete diff, receipts and cited rules, never the author's reasoning or hinted findings.
  • grace5 --help and the generated CLI reference print the installed documentation root, so a fresh session can find the lifecycle documents without a filesystem-wide search. A non-OMP harness receives the same invariants through its own task tools, and a conflicting higher-priority harness policy is a critical stop before dispatch.

Decisions for review

  • D1Harness task facilities own spawn, message, wait, cancel, inspection and transient progress; the GRACE adapter owns authority, isolation, phase selection and closure.
  • D2Preparation is a lifecycle phase, not a separate conversation: a requested material revision is prepared and briefed in the triggering conversation, and only the genuine unresolved owner decision is asked.
  • D3Live execution uses native progress state; the prose checkpoint holds only what is not durably recoverable and is updated on handoff, changed obligation, pause or finish, not on every status read.
  • D4Implementers run baseline, targeted and final evidence; the orchestrating agent validates status and the complete diff at handoff and does not repeat fresh evidence on an unchanged candidate.
  • D5Dispatch packets are role-bounded and carry verified repository and documentation roots, shell convention, change id, original start and current candidate, permitted role and return stage; reviewer packets carry no author reasoning.
  • D6A conflicting higher-priority harness policy is a critical stop before dispatch; a capability fallback uses equivalent native task tools and discloses unavailable independence rather than weakening a gate.
  • D7No OMP path, session file or configuration is a kernel prerequisite; another harness receives the same invariants through its own task tools.

Risks

  • The behavioral evidence is one rehearsal. Only CK5 observes the agent's orchestration, and one batch plus one interruption cannot show behavior on other harnesses, larger or dependent batches, concurrent work, or situations the rehearsal never reaches.
  • The adapter depends on each harness providing native spawning, messaging, waiting and cancellation. A capability fallback must disclose reduced independence, so the fallback path may verify less than the rehearsal demonstrates.
  • Preparing a revision in the triggering conversation shortens the path to an owner decision but can blur preparation with execution. Only an approval of the exact revision authorizes work; approval is never inferred from the conversation.
  • One compact checkpoint replaces broader ledger prose. Anything not durably recoverable and not recorded at handoff, changed obligation, pause or finish can be lost when a session is interrupted.
  • The help output becomes orientation for installed layouts. CK4 sees only the marker, so a wrong path or a package whose installed root differs from this checkout can still satisfy the trace.
