An approval authorizes execution; holding a change for a batch is not a kernel state

Brief for approval. Change C-0008-approval-executes, revision 1, 2026-11-14. Full brief, written by: the author (self), on the owner's instruction to take the cheap path for small changes.

What you get

  • When you approve a change, it can be executed. There is no second decision and no second status: the values "approved" and "approved for execution" become one, "approved".
  • The refusal "approval does not authorize execution" disappears. A run is refused for lack of an approval and for nothing else about the approval.
  • "Approved, hold" or any wording that defers the start is still an approval; the agent does not start until you start the change or a batch, and nothing about the hold is recorded anywhere.
  • Records already written keep their executes flag and Execution element and still validate; the kernel ignores them. The two firmware changes that stand refused today become runnable as they are, without touching their records, once the firmware takes this version.
  • The brief's closing line and the prepare skill ask for one statement: approve, or reject with the reason. The execute skill requires the state "approved".
  • Version 0.6.0, with an upgrade step that refreshes the installed skills and nothing else.
