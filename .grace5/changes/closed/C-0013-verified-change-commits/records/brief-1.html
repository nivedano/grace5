Change commits construct and verify the Change trailer mechanically

Brief for approval. Change C-0013-verified-change-commits, revision 1, 2026-11-17. Full brief, written by: independent reader.

What you get

  • A change's commits are built by one repository routine from an explicit change id and an explicit list of owned paths, so attribution is constructed in the commit path instead of remembered per free-form commit.
  • The routine appends the literal Change: <id> trailer and reads the created commit back — its parsed trailers and its changed-path list — and refuses a missing or mismatched trailer or any read-back failure.
  • It refuses an empty selection and any path outside the supplied list; it never stages all dirty files, never rewrites history and never hides a failed verification, and a failed verification stops the next handoff.
  • grace5-execute and grace5-orchestrate point at the routine for product, test, evidence, review and close-move commits; batch-only ledger commits are attributed by their actual ownership, not to a change whose records they do not carry.
  • No kernel command, schema, record kind, receipt field, approval or closure rule changes, and no version, pin, tag or migration boundary moves; a red test-first commit stays valid.

Decisions for review

  • D1The change id and the owned paths are explicit arguments to the routine; implicit staging and any inference from dirty state are refused.
  • D2The literal Change: <id> trailer is written once and read back from the created commit; a trailer mentioned only in prose does not count as attribution.
  • D3Batch-only ledger commits are attributed by their actual ownership; they are not assigned to a change whose records they do not carry.
  • D4A failed read-back stops the next handoff; repair is a separate, owner-visible operation, never an automatic history rewrite.
  • D5A harness-native verified commit facility is used where one exists; the repository routine is the portable fallback.
  • D6A red test-first commit stays valid because the lifecycle, not the commit routine, decides when evidence is final.

Risks

  • Attribution only improves for commits that go through the routine. A commit made by another path, or by hand, still lacks the trailer, so the failure that motivated the change can recur whenever the routine is bypassed.
  • A stricter routine can block a handoff: a refusal on a mismatched read-back or an out-of-list path stops work until it is resolved. The change keeps a red test-first commit valid and prefers a harness-native verified commit facility where one exists, which limits but does not remove that friction.
  • A read-back failure is reported and never repaired automatically. A genuinely wrong trailer therefore needs a separate, owner-visible repair, which costs time on the very path that already failed.
  • The routine may act only on the supplied paths; if the caller's list is wrong or incomplete, the routine refuses rather than correcting it, so the list itself remains a place where a mistake shows up late.
  • The edited skill text must be repackaged, or the generated-artifact verify check fails and the change cannot hand off.

Approval decisions and effort

  • Rule on the fallback: where a harness already provides a verified commit facility, the change prefers it and keeps the repository routine only as the portable fallback. It is a repository tool, never a kernel command.
  • Accept that attribution covers the commit path the routine owns. Commits made outside it are not forced to carry the trailer; review and the recorded start revision still cover that gap, not the routine.
  • Provide a git worktree whose foreign dirty work is identified rather than committed. The routine stages only the supplied paths and never adopts unknown work, so pre-existing changes must be left alone or handled first.
  • No bench session or manual procedure is required. The work is code and skill text, verified by the type check, the routine's test suite, the generated-artifact verify and the routine's help.
