The conformance suite runs its files in parallel and no file dominates a worker, so a full suite run takes a fraction of today's serial time

Brief for approval. Change C-0010-parallel-conformance, revision 1, 2026-11-14. Full brief, written by: independent reader.

What you get

  • A full conformance run takes a fraction of today's serial time: the suite's test files are rearranged by topic until no file holds a disproportionate share of the tests, so a parallel run's wall time approximates its slowest file rather than the sum of all files.
  • The measured bar: the parallel run's recorded elapsed time comes under half the recorded serial baseline of 396.6 seconds. Parallel execution alone, before any rearrangement, was measured at 230 seconds on this host, so the rearrangement itself must close the remaining gap.
  • The suite's inventory is untouched: no test, assertion or helper is changed, added or removed. A committed baseline of the suite's test titles, taken before the rearrangement, is the reference a check compares against, so anything lost, renamed or added fails the run.
  • Daily use runs the parallel form: the test script of package.json runs bun test --parallel, and the serial command remains valid.
  • AGENTS.md states the measured duration of the parallel run, in place of today's "bun test (about four minutes)" line.
  • Nothing outside the conformance suite, the test script and that one AGENTS.md line is written: no command, schema, record kind, skill, tool or validation mechanism is added.

Decisions for review

  • D1The requirement is a shorter suite run, not a smaller suite: the length sits in scratch-repository construction and real CLI spawns, not in case count, so the cut comes from parallelism and file arrangement and the 57 documented cases stay untouched.
  • D2The runner's own file-level parallelism is the whole mechanism. Measured on this host: 396.6 seconds serial (C-0007 run 4) against 230 seconds parallel before any rearrangement, with identical totals.
  • D3The largest files are split by topic until none dominates a worker; the split is mechanical and is guarded by a committed title baseline rather than a new validation mechanism.
  • D4The test script of package.json runs the parallel form for daily use; the serial command remains valid and is not re-verified by a dedicated check.
  • D5No check carries a timing threshold: speed is evidenced by the recorded elapsed time of the parallel receipt against the recorded serial baseline, and judged in review.
  • D6No release: the version, the pin, the tag and the migration steps stay as they are; a release remains a separate owner-requested change.

Risks

  • The bar rests on an arithmetic premise no check measures: 230 seconds parallel before rearrangement is already above half the serial baseline (198.3 seconds), so meeting the criterion depends entirely on how the rearrangement redistributes the slowest file's time. No check measures per-file time, and sharding and custom runners are excluded, so there is no fallback if splitting by topic is not enough.
  • The numbers are one host's: the same serial suite measured 676 seconds under concurrent load. A parallel receipt recorded under load can miss the bar with no regression, and with no threshold in any check the judgment, with no recorded tolerance, falls to review.
  • The title baseline guards titles, not assertions: a test body weakened behind an unchanged title passes every check, and for the six cases whose tests carry no case id in their titles, which test serves which case is readable only from the test bodies. Review is the remaining guard.
  • The serial command's continued validity is asserted, not verified: no dedicated check runs it, so a file-level dependency introduced by the split would surface only when someone runs the serial form.

Approval decisions and effort

  • Rule on the speed tradeoff with no automated threshold: the under-half judgment is made in review on the parallel receipt's recorded elapsed time, and the decision rests on one host's numbers (396.6 seconds serial recorded, 676 under load, 230 parallel before rearrangement).
  • Accept the unverified serial form: the serial command remains valid without a dedicated re-verification check; its continued working rests on the rearrangement being mechanical and type-checked.
  • The AGENTS.md duration line carries no check: it stays part of the Change and is verified by the independent review of the complete diff, the method's normal home for a documentation line.
  • No bench session and no manual procedure is part of the contract: all three checks are automated, and the owner's effort is this brief and the approval decision itself.
