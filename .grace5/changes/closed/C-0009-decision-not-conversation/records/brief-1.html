An approval records a decision, not a conversation, and a version is an owner-requested release

Brief for approval. Change C-0009-decision-not-conversation, revision 1, 2026-11-14. Full brief, written by: independent reader.

What you get

  • An approval records your decision and nothing else. A new record says the decision is approved, or says it is rejected with your reason. The agent is no longer asked to quote you or to say where you said it.
  • What an approval binds does not change: the hash of the contract, one hash per check, and the hash of the brief you read. Only the echo of the conversation goes.
  • No record already written is rewritten. Every approval in this repository and in a pilot keeps its Source and its sentence, validates as it does today and reads with the same decision and binding; the kernel ignores Source everywhere.
  • A rejected record with no Statement becomes a defect that check reports. A Statement left present but blank is already refused by the shared text type, so this closes the one gap left. An approval's wording is not policed, which is what keeps the records already written validating.
  • A release is a version this repository tags v<version>, and the previous release is the nearest earlier such tag. You ask for a release; one release is one change and may carry any number of closed changes.
  • Only that change bumps package.json, the status line in README and the pin, and adds the migration step for the boundaries its carried changes cross. It verifies an upgrade from the previous release's tag on a clone with one open change.
  • The sentence that made a change altering the state layout, the local ignore file or the skills ship its step in the same change now says the release carrying it ships the step. The existing chain, the pin rule and every existing step stay as they are.
  • This change is not a release: it stays at 0.6.0, writes no step, and its skill edits install at the next release, so it applies the rule it writes down.
  • The reviewer is now handed the approval record with the rest of the hand-over, and must write a blocking finding when a change that is not a release bumps the version, the pin or a step.

Risks

  • An approval record will hold nothing of yours to recognise. The word approved is the same word whoever typed it, while today the quoted sentence is what lets you recognise or disown a record; after this the record's defence is the brief's hash and the review, which reads the conversation only where it has one.
  • Documentation fidelity has no criterion any more. A document or a skill left stating the old rule passes all six checks, and only the reviewer's reading of the diff against the Change stands between you and a stale method.
  • The definition makes the tag the release. A version someone tags is a release by this text, while your decision says creating a version is your explicit request; the kernel cannot tell who asked, so that half is a convention on tagging.
  • The skills change while the version does not. A pilot pinned at 0.6.0 keeps the old skill text until it takes a release of its own, and the pin reads 0.6.0 on both sides, so nothing tells the two states apart.
  • The step obligation moves rather than disappears: a release must add the step for every boundary its carried changes cross, and the only evidence for that is the release's own upgrade verification, which does not exist yet.
  • Two of your decisions share one contract, so one statement answers both. A rejection of the release rule rejects the approval change with it; there is no partial approval of a revision.
  • This change's final evidence waits on C-0007 closing. If it does not close first, evidence taken now stands beside an open change and has to be taken again after it moves.
