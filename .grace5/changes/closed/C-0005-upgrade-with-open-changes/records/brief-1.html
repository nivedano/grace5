upgrade refuses only the open changes a step would touch, and the documents name every way out

Brief for approval. Change C-0005-upgrade-with-open-changes, revision 1, 2026-11-13. Full brief, written by: independent reader.

What you get

  • grace5 upgrade stops refusing because changes are open. Each migration step declares the change ids it would write in the repository at hand: the 0.1.0 to 0.2.0 step declares the closed siblings it moves, the 0.2.0 to 0.3.0 step declares none. upgrade refuses, with no override, when a step in the chain would write an open change, with the fixed phrase "open changes touched by step <from> -> <to>: <id>, <id>". Today it refuses "open changes: <id>, <id>" whenever any change is open, which is what locked the pilot out on 2026-11-13.
  • The pin leaves the candidate and the dirty state. Today .grace5/kernel-version is source like any tracked file, so writing it changes every open change's candidate and dirties the tree. After this change source-identity.md excludes it beside .grace5/changes/**, and the kernel's candidate and dirty computations follow: writing the pin changes no change's candidate. The safety sentence about the pin in source-identity.md and upgrade.md is reworded to this.
  • Every other write a step makes outside the change directories stays source; today those are the .gitignore line of the first step and the installed grace5-* skill directories every step refreshes. The plan lists each such path whose bytes would change as "writes: <path>". With open changes present, upgrade refuses before writing anything, "open changes present; the upgrade would write: <path>, <path>", unless it is given --accept-evidence-loss; then it proceeds and prints "evidence of open changes becomes history: <id>, <id>", which is what the candidate rule already makes true of any source write.
  • With open changes present and no source write pending, the upgrade proceeds with the open changes in place, lists them in the plan as "open, untouched: <id>, <id>", and the post-upgrade check reads them like every other change: same contract and definition hashes, no new defect. Their evidence stands.
  • A change may therefore span kernel versions. Its receipts already carry the kernel of each run; grace5 status will print the kernel a counted result was recorded with whenever it differs from the kernel running now.
  • The documents name the two ways out when a step does touch an open change: close it with the previous kernel, which means running from a checkout at the previous tag, or abandon it. upgrade.md states the relaxed rule and both ways out; the execute and prepare skills say the same in one sentence each. The kernel offers no override.
  • An unreadable pin becomes a refusal like the others: "repository pin is unreadable: <reason>" on standard error with exit 1, and status prints "state: unreadable (<reason>)". Today the kernel exits 1 from its top-level error handler with a line no document names. commands.md lists both phrases.
  • The conformance test for the skill refresh counts refreshes per step, not per link, so the first chain that contains a pin bump no longer fails that test for a reason that is not a kernel defect.
  • The kernel version becomes 0.4.0, tagged v0.4.0 when this change closes. This repository's own pin is written to 0.4.0 by the change directly, and the 0.3.0 to 0.4.0 boundary is a pin bump: no step, only the pin advances.
  • Ledger entry L-23 is amended to the relaxed rule. No command, document, tool or state file is added.

Risks

  • The flag is the way past the second refusal, and the kernel cannot tell who gives it. An agent executing an open change that meets "the upgrade would write" can pass --accept-evidence-loss itself; the printed line names the cost, nothing records who accepted it, and the open changes' clean results are history from then on. For the pilot that motivated the change, with three open changes and installed skills, the skill refresh makes this refusal the likely one, so the choice between losing three sets of final evidence and not upgrading will be made there.
  • "writes: <path>" is a prediction: the plan compares bytes before applying, and a step whose write it does not account for would not be listed. Today the two writes are known; the rule relies on each future step declaring its writes as it declares its ids.
  • Taking the pin out of the dirty state cuts both ways: an upgraded or hand-edited pin never shows as dirty, so a run after an upgrade is recorded clean before the pin is committed, and nothing in the kernel ties a receipt to the pin the tree had. The receipt's kernel attribute is the only trace.
  • The contract does not say which change the pin commit belongs to when several are open, nor that each worktree holding an open change is upgraded on its own, since the pin lives in the checkout and the method puts one change per worktree.
  • "Writes nothing under any open change's directory" holds only if every step declares its ids truthfully. The post-upgrade check catches a changed contract or definition hash and a new defect, not a touched notes.md or log. The declaration is the step author's word, held by review.
  • The refusal that replaces the old one is reachable today only with a step a test injects: the two shipped steps never touch an open change. The phrase and the behaviour rest on CK2 and on review until a future step does.
  • D1 reverses D2 of C-0004 on the same day, after one incident. The ledger entry is amended to the new rule; its removal criterion is not re-examined.
  • The work is done in a temporary clone (D4). Until the push into the shared repository's master succeeds, the commits and the records exist only in the clone that is to be deleted; if the push is refused, nothing is lost only if the clone is kept.
  • The write boundary is nearly the whole repository: the kernel, the skills, the packages, every method document except the schemas, package.json, both READMEs and the pin. Five protected paths and the review are the boundary, and .grace5/changes/closed/** lies outside the candidate, so that protection is held by review alone.
  • The v0.4.0 tag is made by hand at close. No check shows it exists or points at the closing commit.
