A fourth skill, grace5-orchestrate, runs several approved changes in one mostly unattended session, and every skill reads a repository's optional local extensions

Brief for approval. Change C-0007-orchestrate-skill, revision 1, 2026-11-13. Full brief, written by: independent reader.

What you get

  • GRACE 5 ships a fourth skill, grace5-orchestrate. One session takes every open change that is approved for execution and carries each one from start to close. It lists every other open change as left out, with the reason.
  • The orchestrator writes no product code. For each change it starts an implementer subagent that follows grace5-execute and an independent reviewer subagent that follows grace5-review. It reads where a change stands from grace5 status, never from what a subagent says, and it runs grace5 close itself.
  • By default the run does one change at a time, in id order, in the current worktree. Running changes side by side, or in separate workspaces, happens only where a local extension provides and authorizes it.
  • You are asked only at a critical stop. There are four classes: (1) a gate the kernel reserves for you: approving a material revision, a manual observation, disposing a finding; (2) uncommitted work the run did not make, found inside a change's affected paths; (3) an outward-facing or irreversible action with no standing authority: a push, a deploy, creating a branch or a worktree; (4) a required check that still fails, or a blocking finding that remains, after two fix rounds. A fix round is one return of the change to its implementer to correct the product inside the contract.
  • A change at a critical stop is parked with its question, and the run goes on with the later changes that do not depend on it. A later change depends on a parked one when its contract names it or when both list a common affected path; it is then parked too, as waiting. You receive all parked questions together, once, when nothing else can move.
  • Every other decision is the orchestrator's own and is written to a run ledger. The ledger is kept on disk under .grace5/orchestration/runs/, lets a fresh session resume the run, and is committed when the run ends.
  • A repository may keep local instructions as plain prose files in .grace5/extensions/, one topic per file, each saying which roles it addresses. The folder is optional. All four skills tell their reader to read it first and follow what is addressed to their role. The kernel never creates, reads, writes or validates it.
  • An extension may replace a skill's default, may change the number of fix rounds, may add critical classes, and may grant standing authority for outward-facing actions. It can never grant an approval or any other gate the kernel reserves for you.
  • Upgrading from 0.5.0 to 0.6.0 installs the new skill wherever a repository already has the packaged skills installed, and nowhere else, and refreshes the three existing ones. The version becomes 0.6.0.

Risks

  • The orchestrator's rules are prose that a session follows. The kernel still enforces its own gates (approval, required checks, review, close), but nothing mechanical stops an orchestrating session from writing product code itself or from asking too little. The only evidence is one rehearsal.
  • An extension can replace a skill's default and can grant standing authority for pushes and deploys. Extension files are outside every change's reviewed diff and the kernel does not check them. One edited prose file can widen what an unattended run does without anyone reviewing the edit.
  • Every decision outside the four classes is taken without you and only recorded in the ledger. You learn of it by reading the ledger afterwards.
  • Whether a change depends on a parked one is judged by the orchestrator from the contracts and their affected paths. The kernel does not detect overlap. A dependence that neither contract shows is missed.
  • A check that fails for a reason outside the contract costs two fix rounds of subagent work before it reaches you.
  • The upgrade step writes a new skill directory into every repository that upgrades to 0.6.0 and already has the packaged skills. It is automatic, not opt-in per repository.
  • The contract is about three times the target length. More text means more room for a reading you did not intend; the decisions above are the short form to hold it to.
