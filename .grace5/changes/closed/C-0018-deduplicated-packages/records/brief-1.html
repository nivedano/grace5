One canonical skill copy in the source tree, with distribution materialized at build time

Brief for approval. Change C-0018-deduplicated-packages, revision 1, 2026-11-17. Full brief, written by: independent reader.

What you get

  • One maintained copy. skills/ stays the only skill content this repository keeps as source: the four lifecycle skills are authored there once, and the sixteen tracked SKILL.md bodies that exist today become four.
  • Distribution materialized instead of stored. bun run package produces the three layouts, packages/skills/, packages/claude-plugin/skills/ and packages/openpackage/skills/, with their manifests and READMEs at build or release staging, and .gitignore keeps them out of git. The format-specific manifests and the generation logic stay.
  • The same skill bytes. No skill sentence is rewritten: the generated content is compared before and after the layout change, so lifecycle semantics, help text and installed behaviour do not move.
  • A refresh that works where it runs. From a source checkout the refresh mirrors skills/; inside an installed distribution it mirrors the explicitly packaged copy the package carries; it never reads a removed generated directory or the residue of an earlier build.
  • Verification without tracked bodies. Package verification regenerates the packages in memory and reports stale, missing and extra distribution content and stray entries under packages/, and a fresh checkout runs the required checks without anyone manufacturing a missing package directory.
  • Consumers stay whole. Every direct consumer of packages/ is inventoried and either keeps a verified compatible route or is named in the compatibility decision, rather than being left to discover an absent directory.
  • Nothing about identity or release moves. No version, pin, tag, migration row or release belongs to this change; the local grace5-release skill stays where it is and is not shipped; no client rollout and no historical upgrade rewrite happens.

Decisions for review

  • D1skills/ is the sole maintained skill source, and the three distribution layouts are materialized at build or release staging rather than tracked as ordinary source. The tradeoff: a checkout, a diff and an archive no longer contain the distribution bytes, so anything that read them there has to go through the generator instead.
  • D2The generated packages are ignored in the source tree, .gitignore states it, and a fresh checkout runs the required checks with no prior build. The tradeoff: an ignored tree is invisible to git, so a stale generated directory on disk is neither reported nor removed by anything but the generator.
  • D3Package verification needs no tracked package bodies: it regenerates deterministically and detects stale, missing and extra distribution content. The tradeoff: verification pays a regeneration and can judge only what the generator produces, not what a consumer expects to find.
  • D4The CLI refresh resolves canonical content in a source checkout and the explicitly packaged resource in an installed distribution, and never depends on a removed generated directory or an incidental prior build. The tradeoff: two resolution paths must be kept distinct and tested, and a checkout whose generated tree is absent is not a refresh source at all.
  • D5Every direct consumer of packages/ is inventoried and each either has a verified compatible route or is named in the compatibility decision. The tradeoff: a consumer outside this repository can be named but not verified here, and naming it is the honest fallback.
  • D6Symlinks are not assumed to work on Windows, in archives or in installers; the layout is proven with real files. The tradeoff: real files are generated rather than shared by link, and a consumer that depended on a link would break, which the inventory has to catch.
  • D7This change coordinates with the package-owned installation rule and the packaged advisor resource so that neither introduces a second skill source or a duplicate watchdog. The tradeoff: more than one change in this batch touches generation and installation, and they must land in an order that never leaves a packaged resource with no source or two sources.
  • D8No release, version, pin, tag or migration row is part of this change; the release act remains separate and owner-requested. The tradeoff: whether the release must stage or attach the generated trees is not decided here, and stays with the owner.
  • D9The local grace5-release skill is preserved and is not packaged as a shipped skill. The tradeoff: it keeps working from this checkout while packages/ is generated rather than committed, and its inspect-the-generated-diff step has no diff to inspect after this change.

Risks

  • The candidate moves. Source identity counts every tracked path, so removing the generated trees from the index changes the candidate of every revision. Results recorded by other changes in flight, including parked work in this batch, are then of an earlier candidate and must be rerun; nothing warns about that, it is read from the rule.
  • Ignored is not absent. A generated tree left on disk from an earlier build is invisible to git and to the dirty check, and package verification compares against it or overwrites it. A client installed from such a checkout can differ from a fresh one with nothing in git to show it.
  • An empty checkout. A fresh clone, an archive or a CI job has no packages/ until bun run package runs there, so a step that assumes the trees are present, such as installing the plugin from a checkout, packaging the repository as it stands, or the release skill's inspect-the-diff step, can read or ship nothing while every check still passes.
  • External consumers stay unverified. The compatible route the decision requires can be verified inside this repository; a marketplace, an OpenPackage client or a downstream repository that reads packages/ from a checkout can only be named, and its breakage would surface there rather than here.
  • A criterion rests on prose. A recorded passing bun run check will be filed as evidence for the claim that no version, pin, tag or migration row moves, although a type check cannot observe any of them. Only the premise stated in the contract, the limitation recorded above and the reviewer's reading of the diff stand behind that clause.
  • Platforms are decided, not proven. Windows path handling, archives and installers that carry the distribution are settled by a constraint and a decision, not by these five checks, so a consumer that silently used the old mirrored paths fails outside this change's evidence.

Approval decisions and effort

  • Rule on the untracking. Approving removes the three generated layouts and the twelve mirrored SKILL.md bodies from git: what a checkout, a diff and an archive contain changes, and restoring them as ordinary source later would need a new decision.
  • Rule on the consumer inventory. Each direct consumer of packages/ must be verified compatible or named; accept the inventory as complete, or name a consumer it misses.
  • Accept the reruns. Because the candidate of every revision changes when those paths leave the index, approved results of other changes in flight are invalidated and must be rerun after this lands; identifying the affected runs is work this change does not do by itself.
  • Accept the two soft evidences. The identity clause and the one-canonical-copy clause rest partly on the stated premise and the wider suite rather than on a single check that reads them; accept that reading, or ask for a check that reads the index and the version surfaces directly.
  • No bench session is required for this change: all five checks are commands run in this repository plus one index listing, which the executor records. Exercising an installer or an archive on a real platform would be a new check and a separate request.
