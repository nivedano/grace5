Decisions for review

  • D1skills/ is the sole maintained skill source, and the three distribution layouts are materialized at build or release staging rather than tracked as ordinary source. The tradeoff: a checkout, a diff and an archive no longer contain the distribution bytes, so anything that read them there has to go through the generator instead.
  • D2The generated packages are ignored in the source tree, .gitignore states it, and a fresh checkout runs the required checks with no prior build. The tradeoff: an ignored tree is invisible to git, so a stale generated directory on disk is neither reported nor removed by anything but the generator.
  • D3Package verification needs no tracked package bodies: it regenerates deterministically and detects stale, missing and extra distribution content. The tradeoff: verification pays a regeneration and can judge only what the generator produces, not what a consumer expects to find.
  • D4The CLI refresh resolves canonical content in a source checkout and the explicitly packaged resource in an installed distribution, and never depends on a removed generated directory or an incidental prior build. The tradeoff: two resolution paths must be kept distinct and tested, and a checkout whose generated tree is absent is not a refresh source at all.
  • D5Every direct consumer of packages/ is inventoried and each either has a verified compatible route or is named in the compatibility decision. The tradeoff: a consumer outside this repository can be named but not verified here, and naming it is the honest fallback.
  • D6Symlinks are not assumed to work on Windows, in archives or in installers; the layout is proven with real files. The tradeoff: real files are generated rather than shared by link, and a consumer that depended on a link would break, which the inventory has to catch.
  • D7This change coordinates with the package-owned installation rule and the packaged advisor resource so that neither introduces a second skill source or a duplicate watchdog. The tradeoff: more than one change in this batch touches generation and installation, and they must land in an order that never leaves a packaged resource with no source or two sources.
  • D8No release, version, pin, tag or migration row is part of this change; the release act remains separate and owner-requested. The tradeoff: whether the release must stage or attach the generated trees is not decided here, and stays with the owner.
  • D9The local grace5-release skill is preserved and is not packaged as a shipped skill. The tradeoff: it keeps working from this checkout while packages/ is generated rather than committed, and its inspect-the-generated-diff step has no diff to inspect after this change.

Risks

  • +The manifest is written by the generator it verifies. Generation and recording share one code path, so a systematic mistake in the generator, a wrong relative path or a wrong hash, is recorded as the expected value rather than caught by verification; only the suite and the diff against the previously tracked bodies stand outside that loop.
  • +A tracked record is now part of the candidate. Any change to a generated byte therefore has to regenerate and commit the manifest in the same revision, or a fresh checkout verifies generation against a record of different bytes; forgetting it is a red check on an otherwise correct change rather than a silent drift.
  • +The corrected expectation widens nothing. The trace still names two canonical paths and four of the twelve mirrored bodies, so the criteria it shares with the suite and with package verification continue to carry the rest of the one-canonical-copy claim, and the revision adds no check.
