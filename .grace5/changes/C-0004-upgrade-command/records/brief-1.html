The kernel carries its own upgrade: a state version pin, migration steps, and grace5 upgrade

Brief for approval. Change C-0004-upgrade-command, revision 1, 2026-11-13. Full brief, written by: independent reader.

What you get

  • The state carries a version pin: the file .grace5/kernel-version holds the version the state conforms to. grace5 init writes it with the kernel's version when it creates .grace5/; where .grace5/ already exists and the file is missing, the repository is read as 0.1.0. Today no file says which version a repository is at; this repository's README says 0.2.0 in a sentence no command reads.
  • Every command refuses when the pin differs from the running kernel, naming both versions and the command to run. The exceptions are status, upgrade, --help, --version, and init on a repository that has no .grace5/ yet. Today any kernel operates on state laid out for any version.
  • A sixth command, grace5 upgrade, composes the chain of migration steps from the pinned version to the kernel's own version and prints it as a plan in plain words. With --plan it stops there. Otherwise it applies the steps in order, writes the pin after each one, and stops at the first failure with the repository at a consistent version. It refuses while any change is open, naming the open ids, and never downgrades.
  • A migration step is kernel code: one per version boundary whose state layout, ignore lines or skills differ; idempotent, self-verifying, describing itself in one sentence. The first step, 0.1.0 to 0.2.0, moves closed changes under closed/ and appends the line .grace5/changes/closed/*/records/logs/ to the repository's .gitignore when it is absent. The second, 0.2.0 to 0.3.0, writes the pin. A later boundary without a step is a pin bump.
  • Every step refreshes the grace5-* skill directories wherever they already exist under .agents/skills/ or .claude/skills/, from the skills packaged with the kernel, and creates no new location.
  • After the chain, check runs over every change in both locations, and the upgrade fails if any change reports a new defect or a changed contract or definition hash.
  • grace5 status prints the pin and whether it matches the kernel.
  • The pin is an ordinary tracked file, so it is source like any other: an upgrade changes the candidate and leaves the tree dirty until the pin is committed. Because upgrade refuses while a change is open, no change's evidence is invalidated by it.
  • The method document, a new topic file upgrade.md, an upgrading section of the README (three sentences), the help text, the conformance list and the rationale ledger state the facility. From now on a kernel change that alters the state layout, the ignore lines or the skills must ship its migration step in the same change.
  • The kernel version becomes 0.3.0, tagged v0.3.0 when this change closes. This repository's own pin is written to 0.3.0 by this change directly, because upgrade refuses while this change is open; the 0.2.0 to 0.3.0 step is exercised on a clone instead (CK6).

Risks

  • The refusal lands on every repository at once. The moment a repository is read by the 0.3.0 kernel, every command but status and upgrade refuses until upgrade has run, and upgrade itself refuses while that repository has an open change. A pilot with a change in flight cannot take the new kernel until the change closes, unless its pin is written by hand as this repository's is.
  • The pin is source. After every upgrade the tree is dirty until the pin, and whatever the steps moved or appended, is committed; a run before that commit is recorded dirty and counts for nothing. K1 relies on the open-change refusal to keep this harmless, and that refusal is tested only by CK2.
  • The step overwrites grace5-* directories under .agents/skills/ or .claude/skills/ in the repository being upgraded. Local edits there are lost; the contract says the step reports, not that it warns or keeps a copy.
  • Only CK2 reads behaviour, and the same agent writes the tests, the kernel and the CK6 tool. The safety claims of the command (idempotent steps, stop at the first failure at a consistent version, no downgrade, no new defect after the chain) rest on those tests and on the review.
  • .grace5/changes/closed/** is protected, but everything under .grace5/changes/ is outside the candidate and the kernel never reports a protected glob there, so this protection is held by review alone. The first migration step writes exactly that tree in the repositories it upgrades; here it runs only on the clone CK6 makes.
  • The write boundary is nearly the whole repository: the kernel, the skills, the packages, every method document except the schemas, package.json, both READMEs, .gitignore and the pin. Five protected paths and the review are the boundary.
  • The v0.3.0 tag is made by hand at close. No check shows it exists or points at the closing commit.
