close moves the change directory under closed/, so open changes stay in view

Brief for approval. Change C-0003-closed-directory, revision 1, 2026-11-13. Full brief, written by: independent reader.

What you get

  • When grace5 close succeeds, its last step moves the change directory from .grace5/changes/<id>/ to .grace5/changes/closed/<id>/ and prints the new path. Today every change, open or closed, stays a sibling under .grace5/changes/ and only the presence of records/close.xml tells them apart.
  • Closed still means records/close.xml exists. A change under closed/ carries it: status and check read it, run and close refuse it with the fixed phrase "change is closed", and nothing in the kernel moves it back. A directory under closed/ without close.xml is reported malformed, not open and not closed.
  • grace5 init refuses a change id that already exists, open or closed. Today it reports the existing directory and leaves it alone.
  • This repository's .gitignore ignores run logs under closed/ as it already does for open changes, so the moved changes' local logs do not appear as untracked files.
  • The status listing shows the open changes one line each and ends with one line counting the closed ones. status --all also lists the closed ones, each marked closed.
  • The method documents state the new layout, the rationale ledger gains one entry for the mechanism with its removal criterion, and the conformance list gains the new cases.
  • The two changes already closed in this repository, C-0001-kernel and C-0002-pilot-readiness, are moved under closed/ in a records-only commit once the kernel reads them there. Their records are not rewritten.
  • The kernel version becomes 0.2.0, tagged v0.2.0 when this change closes.

Risks

  • The move is the last step and never a closing condition. If it fails after close.xml is written (a locked file on Windows, a permission), the change is closed in place and stays a sibling. The contract does not say what status reports then or whether anything retries the move.
  • Nothing moves a change back, and deleting close.xml under closed/ makes the directory malformed rather than open. A close made by mistake has no undo in the kernel; only git can restore it.
  • The contract does not say how the listing treats a closed change that is still a sibling, which is the state of every pilot repository until it takes this version and moves its own changes (N3, D2). Such a change is closed by K2, but whether the listing counts it among the closed ones or shows it on its own line is not stated.
  • .grace5/changes/closed/** and the two closed changes' directories are open for writing, and everything under .grace5/changes/ is outside the candidate and the dirty state. A record rewritten during the move would be caught by nothing in the kernel; K1 forbids it, and review alone holds that line.
  • The write boundary is nearly the whole repository: the kernel, the skills, the packages, every method document except the schemas, package.json and both READMEs. Four protected paths and the review are the boundary.
  • Only CK2 reads behaviour, and the same agent writes the tests and the kernel. A weakened or missing test turns CK2 green without the behaviour.
  • The v0.2.0 tag is made by hand at close. No check shows it exists or points at the closing commit.
